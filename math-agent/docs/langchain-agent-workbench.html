LangChain 1.4 · learn by running it

An agent is a loop.

A model reads a list of messages. It either answers, or it asks for a tool. Your code runs the tool, adds the result to the list, and asks the model again. Almost everything else in LangChain supports this loop.

    Before you start

    Set up once

    You already have most of this in your project. Every example on this page imports one small file, so you can copy a script and run it straight away.

    1. Update your packages. Your requirements.txt allows langchain>=1.0, but some features here need a newer version.
    1. Keep your GROQ_API_KEY in the .env file, as you do now.
    2. Save this file as llm.py in the folder where you will run the examples.

    To use a different model later, change that one string. For example, "openai:gpt-5.5" needs the langchain-openai package and an OpenAI key. The rest of your agent stays the same.

    Your first question

    What is config?

    config is a plain Python dictionary that you pass as the second argument to invoke(). It holds settings for this run. The model never reads it.

    Think of a clinic. What you tell the doctor is the input. Your patient number is the config. The number never becomes part of the conversation, but the clinic uses it to find your file. In the same way, thread_id tells the checkpointer which saved conversation to load.

        Three kinds of data go into a run

        These are easy to mix up. The question to ask is: who needs to read this?

        ArgumentHoldsWho reads itExample
        inputThe conversationThe model{"messages": [...]}
        configHow to run: which thread, limits, labelsLangChain and the checkpointer{"configurable": {"thread_id": "chat-1"}}
        contextFacts about your app or userYour tools and middlewarecontext=UserContext(user_id="student-1")

        What else can go in config?

        KeyWhat it doesWhen you need it
        configurable.thread_idChooses the saved conversationAny agent with memory
        recursion_limitStops the run after this many graph stepsA hard safety stop. create_agent sets it to 9999, so set your own limit.
        tags, metadataLabels for tracing tools such as LangSmithFinding runs later
        run_nameA readable name for the runTracing and debugging

        Why the extra "configurable" level? Top-level keys are standard settings that every run has. configurable is the slot for values that a specific part needs, and thread_id is there because the checkpointer reads it.

        Four rules that prevent most bugs

        • Checkpointer but no thread_id: you get ValueError: Checkpointer requires one or more of the following 'configurable' keys: thread_id, checkpoint_ns, checkpoint_id.
        • thread_id but no checkpointer: no error, but nothing is saved. The agent forgets everything.
        • One thread_id per conversation. If two users share an ID, they share a conversation. Something like f"{user_id}-{chat_id}" keeps them apart.
        • Build the agent once. InMemorySaver lives inside the object you created. A new one starts empty.

        The 80/20 view

        Twelve ideas cover most agents

        LangChain has a very large API. You can build most agents with the twelve ideas below, and all of them attach to the same loop. Learn them in this order. The first four are enough to build something real.

        The four ideas every agent uses

        1

        Models

        init_chat_model()

        A chat model takes messages and returns one AIMessage. It has no memory and it cannot run code. You saw this in the loop above: each call is a fresh read of the list.

        How to use itCreate it once and share it. Use init_chat_model("provider:name") so that changing provider is a one-line edit.
        Good to knowSet temperature=0 for agents. It makes tool use steadier, although it does not make replies identical.

        Try this

        • Run it twice with temperature=1 in llm.py and compare the replies.
        • Look at usage_metadata. Every message you send costs input tokens, and that matters for memory later.

        Tools

        @tool

        A tool is a normal Python function with the @tool decorator. The model never sees your code. It sees only the name, the docstring and the argument types, so write the docstring as instructions for the model.

        Use a tool whenThe model needs exact maths, live data, private data, or has to change something in the world.
        Skip it whenThe model can answer from its own knowledge, such as rewriting or explaining text.

        The last line of the output is the key idea. The model returned a request to call the tool, and nothing has run yet. The agent is the part that runs it.

        Good tools have

        • A clear name such as search_orders, and a docstring that says when to use it.
        • Type hints on every argument, because they tell the model what to send.
        • Small return values. Tool output goes back to the model and costs tokens.
        • Argument names other than config and runtime, which are reserved.
        Tested: an exception stops the agent

        If a tool raises an exception, the whole run crashes. Your devide and square_root tools raise ValueError, so dividing by zero ends the run. Middleware shows how to send the error to the model instead.

        Try this

        • Delete the docstring and run it. @tool refuses a function with no description.
        • Change the question to "What is the capital of Japan?". Check whether tool_calls is empty.

        Agents

        create_agent()

        create_agent builds the loop for you. It calls the model, runs any tools it asks for, adds the results to the list, and repeats. It stops when the model replies with no tool calls.

        Chain: prompt | model | parserAgent: create_agent
        Who picks the steps?You, when you write the codeThe model, while it runs
        Good forTranslate, summarise, classifyTasks with tools and unknown steps
        Cost and speedOne model call, predictableSeveral calls, varies by task

        Use a chain when you already know the steps. Your test1.py is a good example of that. Use an agent when the model has to decide.

        Look at the second tool call

        The real output shows add(a=33, b=0). The model worked out 21 + 12 by itself and then called the tool with a pointless 0. The final answer is right, but the system prompt said to use tools for calculations. A prompt is a strong request and the model can still ignore it. Small models do this more often, so always read result["messages"] while you are building.

        Two lines you will use all the time: result["messages"] is the full list, and result["messages"][-1].content is the final answer.

        Try this

        • Add a subtract tool and ask a question that needs all three.
        • Ask "What is 2 + 2?" and see if the model bothers to use a tool.
        • Rewrite the system prompt and see if the add(33, 0) habit changes.

        Memory

        checkpointer= + thread_id

        The model remembers nothing, so memory means saving the message list and sending it again. A checkpointer saves the list after each step, under the thread_id from your config.

        Use it whenUsers ask follow-up questions, or a run must pause and continue later.
        Skip it whenEach request stands alone, such as "classify this one email".

        Keep memory after Python restarts

        InMemorySaver is for learning, because it disappears when the program stops. Swap in SQLite to keep chats in a file. First run pip install langgraph-checkpoint-sqlite.

        For a production app, the docs recommend PostgresSaver. Your agent code does not change.

        Memory has a cost

        The saved list is sent to the model on every call, so a long chat uses more tokens each turn. SummarizationMiddleware in Middleware helps with that.

        Try this

        • Fix math_agent.py using the change in the config section, then ask a follow-up question.
        • Print every saved message with agent.get_state(config).values["messages"].

        Structured output

        response_format=ToolStrategy(Schema)

        A plain reply is text for people to read. If your code needs the answer, describe the shape with a Pydantic class and you get a checked Python object back.

        Use it whenThe result goes into a database, a form, a chart or the next step of your program.
        Skip it whenA person simply reads the reply, as in a chatbot.
        Tested: two Groq errors to expect
        • Tools plus a plain schema: response_format=Flashcard with tools gave 400: json mode cannot be combined with tool/function calling. Wrapping it in ToolStrategy(...) fixed it.
        • A question that does not fit the schema: ToolStrategy requires the model to answer through the schema. When it replied in plain text instead, Groq returned 400: Tool choice is required, but model did not call a tool. Keep questions and schemas matched, and catch this error in real apps.

        Try this

        • Add a topic: str field to Flashcard.
        • Change difficulty to allow only "easy" and check what the model does.

        Streaming

        agent.stream(..., version="v2")

        invoke() waits until everything is finished. stream() gives you results as they happen, so a person can see that the agent is working. Pick a mode by what you want to show.

        ModeYou receiveUse it for
        "updates"One item per finished stepProgress such as "Searching..."
        "messages"Each piece of text as it is writtenTyping effect in a chat window
        About the newer API

        The docs recommend agent.stream_events(..., version="v3") for new apps. In version 1.4.9 it prints a warning that it is experimental, and the tool output came back as None in my test. Learn stream() first. It works today, and the ideas carry over.

        Try this

        • Print only the [tools] steps to make a simple activity log.
        • Add a time.sleep(2) inside the tool and watch the steps arrive.

        Runtime context

        context_schema= + ToolRuntime

        Tools often need facts such as the current user ID. You could ask the model to pass the ID, but then the model could get it wrong or be tricked into using another user's ID. Context gives those facts straight to your tool. The model never sees that argument.

        Use it whenA tool needs a user ID, a language, a plan level, or a database connection.
        Skip it whenThe value comes from the conversation, such as the city in "weather in Kandy". That belongs in a normal tool argument.

        Both students asked the same question and got different answers, because each run had different context. The runtime argument is filled in by LangChain and is hidden from the model.

        Try this

        • Print get_my_grades.args. You will see that runtime is not there.
        • Add a language: str field to UserContext and use it in the tool's reply.

        Middleware

        create_agent(middleware=[...])

        Middleware is code that runs at set points in the loop: before the model, after the model, or around a tool call. You add features to your agent without changing the loop. LangChain includes many, and you can write your own in a few lines.

        Learn these built-in ones first

        MiddlewareSolves this problem
        ModelCallLimitMiddlewareThe agent loops or spends too much
        ToolCallLimitMiddlewareOne tool is called too many times
        ToolErrorMiddlewareA tool error crashes the run
        ToolRetryMiddleware, ModelRetryMiddlewareA network or rate-limit error should be retried
        ModelFallbackMiddlewareOne provider is down, so try another model
        SummarizationMiddlewareThe chat has grown too long
        HumanInTheLoopMiddlewareA person must approve a tool call
        PIIMiddlewarePrivate data such as emails should be hidden

        Write your own with a decorator

        DecoratorRunsExample use
        @dynamic_promptWhen the system prompt is builtDifferent prompt for each user
        @before_modelBefore each model callTrim old messages
        @after_modelAfter each model callCheck the reply
        @wrap_model_callAround each model callSwitch model during a run
        @wrap_tool_callAround each tool callLogging, permission checks

        Turn a crash into something the model can handle

        The handler is required, and it chooses what the model sees. It sends a message for ValueError and returns None for everything else, so internal errors stay out of the conversation.

        Tested: three things to remember
        • Set a limit. create_agent has a default recursion_limit of 9999, so a stuck agent can run for a long time. Your single-tool-agent already uses ModelCallLimitMiddleware, which is the right habit.
        • Check for the limit message. With exit_behavior="end", the last message becomes Model call limits exceeded: run limit (1/1). Tools may already have run by then.
        • Summaries lose details. With an aggressive setting (summarise after 5 messages), my test agent forgot the user's name. Use a higher trigger, and keep important facts in long-term memory.

        Try this

        • Add ToolErrorMiddleware to your math agent, then ask it to divide by zero.
        • Change Learner(level="beginner") to "expert" and compare the replies.
        • Set run_limit=1 and print the last message.

        Human approval

        HumanInTheLoopMiddleware + Command(resume=...)

        Some actions should not happen without a person. This middleware pauses the agent just before a chosen tool runs. Your program shows the request to a person, then resumes with their decision. The paused run is saved by the checkpointer, so it can even wait for hours.

        Use it whenA tool sends messages, spends money, deletes data, or changes a live system.
        Skip it whenA tool only reads harmless data. Too many approvals become annoying, and people stop reading them.
        DecisionWhat happensShape
        approveThe tool runs as requested{"type": "approve"}
        rejectThe tool does not run. The model gets your message.{"type": "reject", "message": "Do not send this."}
        editThe tool runs with your changed arguments{"type": "edit", "edited_action": {"name": "send_email", "args": {...}}}
        respondYour message is returned as the tool's result{"type": "respond", "message": "Blue."}
        Two details
        • This needs a checkpointer and a thread_id, because the paused run has to be saved somewhere.
        • interrupt_mode="per_call" needs langchain 1.4.6 or newer. The docs recommend it for new agents. In this mode your decisions are a dictionary keyed by interrupt ID.

        Try this

        • Change the decision to {"type": "reject", "message": "Do not send this."}. The "EMAIL SENT" line should not appear.
        • Replace the automatic decision with input("Approve? y/n ") so that you decide while it runs.

        Retrieval (RAG)

        a @tool that searches your data

        RAG sounds complicated, but in an agent it is just a search tool. The model asks for a search, reads what comes back, and answers from it. This gives the model knowledge it was not trained on, such as your notes or company documents.

        Use it whenAnswers must come from your own documents and you want to cite them.
        Skip it whenThe data is small enough to paste into the system prompt.

        This search only matches words, which keeps the idea easy to see. To search by meaning, replace the inside of search_notes with a vector store, such as InMemoryVectorStore from langchain_core.vectorstores, and call similarity_search(query, k=3). You will need an embedding model for that as well. The agent code stays the same.

        Try this

        • Ask something that is not in the notes, such as "Do you sell gift cards?". It should say that it does not know.
        • Load NOTES from a text file of your own.

        Sub-agents

        an agent inside a @tool

        A multi-agent system can be this simple: wrap one agent in a tool, and give that tool to another agent. The main agent hands work to the specialist, and only the final result comes back. The specialist's long working steps stay out of the main conversation.

        Use it whenOne agent has too many tools, or two jobs need conflicting instructions.
        Skip it whenOne agent works. Each extra agent adds model calls, cost and more ways to fail.

        Notice the dollar sign in the output. Nobody mentioned a currency, so the model added it by itself. Check details like this when agents pass text to each other.

        Try this

        • Add a second specialist, such as a writer_agent, and let the main agent use both.
        • Print result["messages"] and notice that the specialist's own tool calls are not there.

        Long-term memory

        store= + runtime.store

        A checkpointer remembers one conversation. A store remembers facts across all conversations, such as "this user prefers Python examples". You decide what is saved, usually with a tool.

        CheckpointerStore
        SavesThe whole message listOnly the facts you choose
        Organised bythread_idNamespace and key, often a user ID
        Lasts forOne conversationAll conversations
        Think of it asThe chat transcriptA notebook about the user

        The two invoke() calls share no messages and no thread, but the second one still found the preference. InMemoryStore is also for learning only, and is lost when Python stops.

        • Run the second question with user_id="student-2". It should find nothing.

        Find the fix

        Start from the problem you can see.

        Your agent...Reach for
        forgets what was just saidCheckpointer and a stable thread_id. Build the agent once.
        forgets after a restartSqliteSaver instead of InMemorySaver
        forgets the user next weekA store
        gives text your code cannot useToolStrategy with a Pydantic class
        feels frozen while it worksstream()
        crashes when a tool failsToolErrorMiddleware
        loops or uses too many tokensModelCallLimitMiddleware
        hits the model's token limit in long chatsSummarizationMiddleware
        could do something riskyHumanInTheLoopMiddleware
        needs to know who the user isRuntime context
        does not know your documentsA retrieval tool
        picks the wrong toolBetter names and docstrings, then fewer tools or sub-agents
        does something and you cannot see whyPrint result["messages"]. Later, try LangSmith tracing.
